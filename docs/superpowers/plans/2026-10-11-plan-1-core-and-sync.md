# Field Inventory: Plan 1, Scaffold, Domain Core and `syncMovements`

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A tested server core: the project scaffold, three Prisma/libSQL databases with a migration runner, pure domain logic for the ledger, balances, count reconciliation and exception detection, and the `syncMovements` server function that ingests offline outbox batches.

**Architecture:** Domain rules are pure functions in `src/domain/` (movements and context go in, effects come out). `src/server/sync/` does only I/O: it loads a `ProcessContext` from the warehouse/catalog databases, calls the pure `processMovement`, and persists the effects, with one transaction per movement. The same migration runner and URL template serve local `file:` databases (tests and dev) and Turso.

**Tech Stack:** pnpm, TanStack Start (React), Mantine 8, Prisma 7 (`prisma-client` generator, `@prisma/adapter-libsql` / `PrismaLibSql`), `@libsql/client`, Zod 4, Biome 2, Vitest, fast-check.

**Spec:** `docs/superpowers/specs/2026-10-11-field-inventory-design.md` (§3, §5, §7, §9, §10; milestones 1–3).

**Out of scope (later plans):** handheld storage, outbox and UI (plan 2, after the Turso browser sync spike), supervisor and admin (plan 3), Playwright E2E (plan 4), Turso Platform API provisioning (plan 3), user authentication (plan 2). In this plan `syncMovements` trusts the `deviceId` and `userId` in the payload.

## Global Constraints

- Package manager **pnpm**. TypeScript `strict: true`.
- **Biome is the only linter/formatter.** No ESLint or Prettier packages or configs.
- Three databases, each with its own Prisma schema and generated client: `global`, `catalog`, `warehouse` (one warehouse DB per warehouse, identical schema). All use `provider = "sqlite"` and the libSQL driver adapter.
- Migrations are SQL files generated by `prisma migrate diff` and applied by our own runner (`src/server/db/migrate.ts`), never by `prisma migrate deploy`.
- Warehouse DB URL comes from env `WAREHOUSE_DB_URL_TEMPLATE` with `{name}` placeholder. Default is `file:.data/{name}.db`. Auth token from optional env `TURSO_GROUP_AUTH_TOKEN`.
- Movement `id` is a client UUID (`z.uuid()`). `seq` is the server-assigned INTEGER PRIMARY KEY.
- All quantities are integers.
- `StockBalance.qty` may be negative. Only the server writes it.
- Clock skew threshold: env `CLOCK_SKEW_THRESHOLD_MS`, default `120000`.
- Stuck transfer threshold: env `TRANSFER_STUCK_HOURS`, default `24`.
- Count tolerance: `product.countTolerance ?? category.countTolerance ?? 0`, compared as `Math.abs(variance) <= tolerance`.
- Auto-adjust reason code is `COUNT_AUTO`.

## Spec clarification (confirmed in plan review)

Convergence is guaranteed **modulo open exceptions**. With finite tolerance, a late movement can either be auto-corrected or raise `LATE_MOVEMENT`, depending on arrival order, and the balance stays un-adjusted until a supervisor resolves it. `NEGATIVE_BALANCE` reflects transient states, so it is also order-dependent. The property tests therefore assert:
- (a) order-independent balances for any movement set with no `COUNT`
- (b) order-independent balances with `COUNT`s when tolerance is `Infinity`
- (c) for any order and any tolerance, every (sku, location) whose balance differs from the tolerance-`Infinity` result has an `OPEN` `COUNT_VARIANCE` or `LATE_MOVEMENT` exception

## Review Focus

1. **Same movement id resent with a different payload.** The first one wins: the row is `duplicate`, and the stored movement and balances are unchanged. Test in Task 10.
2. **A movement with `occurredAt` exactly equal to a count's.** It counts as happening *before* the count, so it's included in `expected`. Test in Task 5.
3. **A batch mixing assigned and unassigned warehouses.** Unassigned rows are `invalid('WAREHOUSE_NOT_ASSIGNED')` and the other rows are still accepted. Test in Task 10.
4. **Malformed physical inputs** (MOVE with `from === to`, `qty` of 0 or negative or fractional, ADJUST of 0, COUNT negative). These are Zod-invalid, so they come back as per-row `invalid` and never break the batch. Tests in Task 3 (schema) and Task 10 (row-level result).
5. **Device clock far in the future** (`occurredAt` > server now + threshold). The movement is still accepted (it happened physically) and `CLOCK_SKEW` is raised once per device per warehouse while the previous one is open. Test in Task 10.

### Task 5: Count reconciliation and late-movement correction

**Files:** Create `src/domain/count.ts`, `tests/domain/count.test.ts`

**Interfaces:**
- Consumes: `movementDeltas`, `Movement`, `ExceptionDraft`
- Produces:
  - `expectedAt(binLedger: Movement[], count: Movement): number`. The sum of `movementDeltas` for this count's (sku, `toLocationId`) over movements with `occurredAt <= count.occurredAt`, **excluding** system ADJUSTs whose `ref === count.id`. A tie on `occurredAt` counts as before the count (Review Focus 2).
  - `type CountOutcome = { kind: 'none' } | { kind: 'auto_adjust'; adjust: Movement } | { kind: 'exception'; exception: ExceptionDraft }`
  - `reconcileCount(count: Movement, binLedger: Movement[], tolerance: number, newId: () => string): CountOutcome`
    - `variance = count.qty - expectedAt(...)`
    - 0 → `none`
    - `|variance| <= tolerance` → `auto_adjust`: system ADJUST, `qty = variance`, `reasonCode 'COUNT_AUTO'`, `ref = count.id`, same sku/location/`occurredAt` as the count, `userId`/`deviceId` from the count
    - otherwise → `COUNT_VARIANCE` with `details { observed, expected, variance, tolerance }`
  - `findAffectedCount(late: Movement, binCounts: Movement[]): Movement | null`. Returns the earliest accepted COUNT on a key that `late` touches with `count.occurredAt > late.occurredAt`.
  - `correctForLateMovement(count: Movement, binLedgerIncludingLate: Movement[], tolerance: number, newId: () => string, lateId: string): CountOutcome`
    - `totalAdjust = count.qty - expectedAt(count, ledger)`
    - `existing = sum(qty of system ADJUSTs with ref === count.id)`
    - `correction = totalAdjust - existing`
    - 0 → `none`
    - `|totalAdjust| <= tolerance` → `auto_adjust` with `qty = correction`
    - otherwise → `LATE_MOVEMENT` with `movementIds [count.id, lateId]` and `details { observed, expected, existingAdjust: existing, correction }`

- [ ] **Step 1: Write failing tests**
  - Ledger `+10` at 09:00, COUNT 8 at 10:00:
    - tolerance 5 → `auto_adjust` qty −2, `ref === count.id`, `reasonCode 'COUNT_AUTO'`
    - tolerance 1 → `COUNT_VARIANCE` with `expected 10, variance -2`
  - COUNT equals expected → `none`
  - Tie: PICK 3 at exactly 10:00 and COUNT at 10:00 → expected includes the pick
  - `expectedAt` ignores this count's own auto-adjust, but includes another count's auto-adjust
  - Late: `+10` 09:00, COUNT 8 10:00 already adjusted −2, then late PICK 3 at 09:30:
    - tolerance 5 → `auto_adjust` qty +3 (total adjust becomes +1)

### Task 7: `processMovement`, the pure orchestrator

**Files:** Create `src/domain/process.ts`, `tests/domain/process.test.ts`

**Interfaces:**
- Consumes: Tasks 4–6
- Produces:

```ts
export interface ProcessContext {
  balances: Map<string, number>        // current balances for keys the movement touches
  binLedgers: Map<string, Movement[]>  // full ledger for each touched key
  openNegativeKeys: Set<string>
  tolerance: number                    // resolved for movement.skuId
  pickLine: { id: string; qtyRequested: number } | null
  pickedBefore: number
}
export interface Effects {
  movements: Movement[]                // the input movement first, then any system ADJUSTs
  balanceDeltas: BalanceDelta[]        // aggregated over all `movements`
  exceptions: ExceptionDraft[]
}
export function processMovement(m: Movement, ctx: ProcessContext, newId: () => string): Effects
```

- Order of evaluation:
  1. Deltas of `m`, then `detectNegative` on them.
  2. If `m` is COUNT → `reconcileCount`.
  3. Else, for each touched key, `findAffectedCount` against that key's ledger plus `m` → `correctForLateMovement`. A resulting auto-adjust's deltas are added, and `detectNegative` is re-run against balances after `m`.
  4. If PICK with a line → `detectOverPick`.

  - Late PICK before an adjusted count, within tolerance → 2 movements, and net delta on that key is 0 (pick −3, correction +3)
  - Late PICK beyond tolerance → `LATE_MOVEMENT`, delta −3

### Task 10: `syncMovementsCore`

**Files:** Create `src/server/sync/sync-movements.ts`, `tests/server/sync-movements.test.ts`

**Interfaces:**
- Consumes: Tasks 2, 3, 6, 7, 9
- Produces:

```ts
export type RowResult =
  | { id: string; status: 'accepted' }
  | { id: string; status: 'duplicate' }
  | { id: string | null; status: 'invalid'; reason: string }   // reason: zod message | 'UNKNOWN_SKU' | 'UNKNOWN_LOCATION' | 'INACTIVE_LOCATION' | 'UNKNOWN_PICK_LINE' | 'WAREHOUSE_NOT_ASSIGNED'
export type SyncResponse =
  | { status: 'ok'; results: RowResult[]; exceptions: ExceptionDraft[]; serverTime: string }
  | { status: 'UPDATE_REQUIRED' | 'DEVICE_REVOKED' | 'DEVICE_UNKNOWN' | 'WAREHOUSE_NOT_READY'; serverTime: string }
export interface SyncDeps {
  global: GlobalClient; catalog: CatalogClient
  warehouseDb(name: string): WarehouseClient
  now(): Date; newId(): string
  clockSkewThresholdMs: number; transferStuckHours: number
}
export function syncMovementsCore(deps: SyncDeps, rawInput: unknown): Promise<SyncResponse>
```

- `SCHEMA_VERSION` for the client protocol is `SCHEMA_VERSIONS.warehouse`.
- Flow:
  1. Parse `syncBatchSchema`. If the envelope is invalid, throw a Zod error; the wrapper turns it into a 400.
  2. Version mismatch → `UPDATE_REQUIRED`.
  3. Device not found → `DEVICE_UNKNOWN`. Revoked → `DEVICE_REVOKED`.
  4. Parse each row with `movementInputSchema`; failures become `invalid`.
  5. Rows for warehouses not assigned to the device → `invalid('WAREHOUSE_NOT_ASSIGNED')`.
  6. Any targeted warehouse whose `schemaVersion` differs → whole response `WAREHOUSE_NOT_READY`.
  7. Sort the valid rows by `(occurredAt, id)`. For each one, in `withMovementTx`: if the id exists → `duplicate`; validate references → `invalid(reason)`; otherwise `loadContext` → `processMovement` → `persistEffects` → `accepted`. A unique-constraint error on insert maps to `duplicate`.
  8. For each warehouse touched:
     - insert a `DeviceClockSample`
     - run `detectClockSkew`, deduplicated against an open `CLOCK_SKEW` for the device
     - run `findStuckTransfers`, whose `inRefs` come from each counterpart warehouse's TRANSFER_IN refs
     - persist those exceptions
  9. Return every exception persisted in this call.

- [ ] **Step 1: Write failing tests**, using `createTestEnv()` and a fixed `now`
  - Happy path: ADJUST +10 then PICK 3 → both `accepted`, balance 7, and `serverTime` equals `now().toISOString()`
  - Resent with the same id and a different qty → `duplicate`, balance unchanged (Review Focus 1)
  - Mixed batch with `qty: 0` and an unassigned warehouse → those rows are `invalid` with the right reasons, and the valid row is `accepted` (Review Focus 3, 4)
  - Unknown SKU → `invalid('UNKNOWN_SKU')`. Inactive location → `invalid('INACTIVE_LOCATION')`.
  - `schemaVersion: 0` → `UPDATE_REQUIRED`. Revoked device → `DEVICE_REVOKED`. In both cases no `Movement` rows are written.
  - Rows are processed in `occurredAt` order even when sent out of order: with product tolerance 5, COUNT 8 at 10:00 sent before ADJUST +10 at 09:00 gives an auto-adjust of −2, not +8.
  - `sentAt` 5 min ahead of `now` → movement `accepted`, one `CLOCK_SKEW` exception. A second batch → no second exception (Review Focus 5).
  - TRANSFER_OUT at `now − 25h` with no TRANSFER_IN in the counterpart warehouse → `TRANSFER_STUCK`. After the TRANSFER_IN is synced, a later out with the same ref isn't flagged.
