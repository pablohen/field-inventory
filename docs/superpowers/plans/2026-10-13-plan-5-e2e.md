# Plan 5: Multi-device E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove the spec's end-to-end success criterion. Two offline handhelds and one supervisor end with the same balances and the same open exceptions under every reconnect order. A movement recorded offline on a device that is then revoked is kept, not lost.

**Architecture:**
- **Server fix:** a late movement can make an earlier count consistent. When it does, the stale `COUNT_VARIANCE` is now closed by the system, so open exceptions no longer depend on arrival order. This is done in the pure domain and persisted in the same sync transaction.
- **Test infrastructure:** Playwright fixtures sign in two handheld contexts (each with its own OPFS) and one desk context against Turso dev DBs. A test-only reset script returns the dev warehouse to its seeded state before each test.
- **Specs:** the multi-device specs are table-driven over reconnect orders.

**Tech Stack:** Playwright (Chromium) and Vitest. Everything else is the existing stack: TanStack Start, Prisma 7/libSQL/Turso, `@tursodatabase/sync-wasm`, and Mantine.

## Global Constraints

- Playwright runs Chromium only. Specs use `context.setOffline(true)` for offline, as §9.2(5) requires.
- Multi-device specs need real browser replicas, so they are skipped unless `E2E_TURSO=1`, which points at seeded Turso dev DBs. Without credentials, report the specs as written but not run (DONE_WITH_CONCERNS). Never fabricate a pass.
- The ledger is append-only: no app code deletes a movement, exception, warehouse, location, product, user or device. Only the test-only reset script (Task 2) deletes rows, and it refuses to run unless `E2E_TURSO=1` and `E2E_ALLOW_RESET=1`. Nothing under `src/` imports it.
- A movement recorded offline is never lost. If it fails validation, loses a race, or comes from a revoked device, the outbox keeps it and it can be exported (§1, §9.1).
- Counts are blind. Handheld screens never show the expected quantity (§5.4.4).
- Biome is the only linter. Use pnpm and strict TypeScript. The gate is `pnpm format && pnpm lint && pnpm typecheck && pnpm test`, plus `pnpm build` for any route or `.fn.ts` change.
- CI runs `biome ci`, `typecheck`, `test` and `e2e` (§10).

## Decisions (user rulings)

- **D1. A late movement supersedes a stale count exception.** This applies when a late movement re-runs a count's reconciliation (§5.5 `LATE_MOVEMENT`) and the corrected total variance is within tolerance (`|observed − expected| ≤ tolerance`).
  - The server resolves every OPEN `COUNT_VARIANCE` or `LATE_MOVEMENT` exception whose `movementIds[0]` is that count's id.
  - Resolved fields: `status 'RESOLVED'`, `resolution 'SUPERSEDED'`, `resolvedBy 'system'`, `resolvedAt` now, `version` +1, and the note `A later-arriving movement made this count consistent`.
  - This happens in the same transaction as the late movement.
  - Any non-zero correction is still written as the `COUNT_AUTO` adjust, as today.
  - When the corrected variance is over tolerance, behaviour is unchanged.

## Review Focus

1. **A supervisor resolving a count exception while a late movement supersedes it.** The version bump must make the slower writer get the desk's existing 409/CONFLICT, never a double resolution (Task 1).
2. **Two handhelds reconnecting at the same moment.** Both batches must be accepted, and the balances must equal the sequential orders' balances (Task 3, the `together` order).
3. **The handheld's local stock view after both devices have synced and pulled.** It must show the same balances as the desk, and must not mix in stale optimistic values (Task 3).
4. **A revoked device that comes back online with pending rows.** Its pending rows stay pending, it shows the revoked state, and export still works. After a restore, sync drains to 0 pending (Task 4).
5. **Re-running the e2e suite against the same dev DBs.** It must start from the seeded state every time, never from the previous run's leftovers (Task 2, reset before each test).

### Task 3: Two handhelds and a supervisor under every reconnect order

**Files:**
- Create: `e2e/multi-device.spec.ts`

**Interfaces:**
- Consumes: Task 2 fixtures, helpers and `CONTESTS`, and Task 1's D1 behaviour.

- [ ] **Step 1: Write the spec.** It is table-driven over `RECONNECT_ORDERS = ['A then B', 'B then A', 'together'] as const`, with one `test` per order. Each test:
  1. Takes both handheld contexts offline.
  2. Has A record its two contest actions, then B record its two. A's MOVE out of `A-01` happens before B's COUNT of `A-01`.
  3. Expects `pendingCount` 2 on each handheld.
  4. Reconnects in the given order.
     - `together` sets both contexts online and calls `syncNow` on both with `Promise.all`.
     - The sequential orders bring one device online and sync it to 0 pending before the other comes online.
  5. Checks the desk, after reload:
     - `deskQty`: `A-01` = 4, `A-02` = 6, `A-04` = −16, `A-05` = 16.
     - `openExceptions` equals exactly `[{ type: 'NEGATIVE_BALANCE', skuId: 'prod-4', locationId: 'wh-1-A-04' }]`. No COUNT_VARIANCE appears in any order, which proves D1 end to end.
  6. Checks both handhelds: after one more `syncNow` (to pull), `handheldQty` matches the desk for all four bins.
  7. Has the supervisor resolve:
     - open the NEGATIVE_BALANCE exception
     - use the Adjust action with +16 at `A-04` (reason `Found`)
     - then `openExceptions` is `[]` and `deskQty(A-04)` is 0
- [ ] **Step 2: Run** `E2E_TURSO=1 E2E_ALLOW_RESET=1 pnpm e2e e2e/multi-device.spec.ts`. Expected: 3 passed. Without credentials, report the spec as written but not run.
